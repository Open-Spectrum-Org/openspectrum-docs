## 1. Purpose

Open Spectrum is evolving from a simple event-logging application into an **intelligent data capture, analysis, insight, and investigation platform for parents of neurodivergent children**.

This document captures the product insights that emerged from a detailed parent review and should guide the next major backend, frontend, data-model, and interaction refactoring.

The most important architectural principle is:

> **Build a flexible underlying data model and modular intelligence layer so that Open Spectrum can adapt to each child and each parent's questions over time.**

The application should not force every parent into the same taxonomy, workflow, or set of questions.

---

# 2. Core Product Philosophy

Open Spectrum should evolve around this loop:

**Capture → Data → Analysis → Insights → Focus → Prompt → Capture**

And eventually:

**Capture → Data → Focus → Analysis → Hypothesis → Community → Evidence → Insights → Better Capture**

The system should become increasingly intelligent while keeping the parent in control of their data.

Three principles should guide the architecture:

### 1. The parent owns the data

Parents should be able to export their underlying observations and use them independently.

### 2. The parent supplies the question

Instead of simply asking parents to log everything, Open Spectrum should allow a parent to say:

> "Here's what I'm trying to understand."

The system then determines what data, questions, analyses, and reports are relevant.

### 3. Open Spectrum adapts to the parent

Frequently used actions should become easier to access. Prompts should become more relevant. Focus Areas should influence the experience. The system should learn what is useful without becoming intrusive.

---

# 3. Major Architectural Change: Modularize the Application

The existing application should be refactored away from a monolithic design toward independent modules sharing a common underlying data model.

Potential modules include:

* **Child Profile**
* **Capture / Logging**
* **Prompting**
* **Timeline / History**
* **Tags / Taxonomy**
* **Assessment / Scoring**
* **Focus Areas**
* **Analysis**
* **Insights**
* **Reports**
* **Data Export**
* **Hypotheses**
* **Parent-to-Parent Ecosystem**

These should be loosely coupled.

Each module should be independently replaceable or enhanced, including with AI.

For example, the Prompting module should not need to know how the Timeline UI works. Both should consume the shared data model.

---

# 4. Mobile vs. Web: Different Jobs

Open Spectrum should explicitly recognize that mobile and web are different consumption environments.

## Mobile: Capture

Mobile should optimize for:

* Fast event entry
* Voice/speech input
* Quick taps
* Frequently used logging options
* Minimal navigation
* Low cognitive load
* Contextual prompts
* Immediate capture of observations

The parent may be busy, stressed, or in the middle of an event.

The goal is:

> **Capture useful information with as little friction as possible.**

## Web/Desktop: Understand

The web experience should optimize for:

* Timeline review
* Analysis
* Trends
* Comparisons
* Insights
* Reports
* Focus Areas
* Data exploration
* Charts
* Longitudinal analysis
* Export

The goal is:

> **Help the parent understand what has been happening.**

The same underlying data model should power both experiences.

---

# 5. Data Model: Separate Event Time from Record Time

This is a fundamental data-model change.

Every observation/event should distinguish:

### Event Time

When the event actually happened.

### Record Time

When the parent entered the information into Open Spectrum.

For example:

```text
Event:
    Child had difficult morning

Event Time:
    2026-09-01 08:15

Recorded:
    2026-09-03 21:40
```

A parent may remember something from yesterday or several days ago and enter it later.

Therefore:

> **Event Time is the primary analytical time dimension.**

Record Time should remain as audit/history metadata.

All trend analysis, timelines, correlations, reporting, and longitudinal analysis should primarily use Event Time.

The data model should support:

* Exact timestamps
* Dates
* Approximate dates
* Relative dates when necessary
* Unknown time
* Start/end times where appropriate
* Record timestamp
* Potentially timezone

---

# 6. Events Should Be Rich Objects, Not Binary Records

The current model can be too simplistic.

For example:

```text
Food → Dairy → Taken
```

is not sufficient.

An event should potentially capture:

* What happened
* When it happened
* Context
* Quantity
* Duration
* Assessment
* Severity
* Effect
* Tags
* Free-text observation
* Structured attributes
* Parent confidence, where useful
* Relationship to other events

The exact fields should be flexible rather than requiring every event to use the same schema.

---

# 7. Assessment / Quality / Value

An observation should be able to record **how something went**, not merely whether it happened.

Different event types may require different assessment dimensions.

Examples:

### Mood

```text
1–5
Very low → Very high
```

### Sleep

```text
1–5
Very poor → Very good
```

### Behavior

```text
Severity: 1–5
```

### Food reaction

```text
Adverse / Neutral / Positive
```

### Medication effect

```text
Worse / No change / Better
```

The data model should therefore support configurable assessment scales.

Do not hard-code one universal scoring system.

---

# 8. Parent-Defined Custom Tags

The predefined taxonomy should not constrain the parent.

Parents should be able to create their own tags.

Examples:

* School morning
* Sensory overload
* Weekend
* Transition
* Grandma's house
* Specific food
* Specific routine
* Specific behavior

Custom tags should:

* coexist with system tags
* support multiple tags per event
* be searchable
* be filterable
* be usable in analysis
* potentially become part of the child's vocabulary/profile

The principle is:

> **The application adapts to the child rather than forcing the child into the application's taxonomy.**

---

# 9. Adaptive Logging Interface

The logging experience should learn from usage.

Frequently used logging actions should gradually become more prominent.

For example:

```text
Frequently used
----------------
Mood
Sleep
Morning behavior
Medication

More
----------------
Everything else
```

The system should consider:

* Frequency
* Recency
* Context
* Time of day
* Focus Areas
* Parent preferences

Do not create an unstable UI that constantly rearranges itself.

Ordering should adapt gradually and predictably.

The goal is:

> **The parent should not have to adapt to Open Spectrum. Open Spectrum should adapt to the parent.**

---

# 10. Timeline: Optimize for Information Density

The current one-event-per-card approach is visually clean but can become inefficient.

Parents need to review:

* Today
* Yesterday
* Previous days
* Weeks
* Patterns over time

The Timeline should therefore become a **review tool**, not simply a collection of attractive cards.

Consider:

* Compact rows
* Date grouping
* Dense summaries
* Expandable details
* Filtering
* Tag filtering
* Focus filtering
* Assessment indicators
* Multiple events per day
* Desktop/table-oriented views

The user should be able to scan a large amount of history quickly.

---

# 11. Focus Areas — A Central Product Concept

A parent should be able to define one or more **Focus Areas**.

Examples:

> "Mornings have been getting worse."

> "Is sleep getting better?"

> "Could melatonin be affecting behavior?"

> "I want to understand the relationship between food and mood."

> "Why are school mornings harder than weekends?"

Focus Areas should become a **dynamic intelligence layer across the entire application**.

A Focus Area is more than a tag.

It represents:

> **Something the parent is actively trying to understand.**

---

# 12. Focus Areas Should Influence Everything

Once a parent establishes a Focus Area, Open Spectrum should intelligently adapt multiple modules.

## Capture

Suggest relevant observations to record.

## Prompting

Ask questions relevant to the Focus Area.

## Timeline

Allow the parent to view relevant historical events.

## Analysis

Identify relevant data, even if those events were not explicitly tagged with the Focus Area.

## Insights

Surface observations and patterns relevant to the Focus Area.

## Reports

Generate reports organized around the Focus Area.

## Hypotheses

Generate potential explanations worth investigating.

The parent should not have to manually connect every relevant event.

The system should use the underlying data model to assemble relevant evidence.

---

# 13. Focus Areas Should Be Structured Internally

A Focus Area should eventually contain concepts such as:

```text
Focus Area
-----------
id
title
description
created_at
status
related_tags
related_event_types
relevant_variables
questions
hypotheses
analysis_config
```

For example:

```text
Focus:
    Difficult mornings

Possible relevant variables:
    Sleep duration
    Sleep quality
    Wake time
    Previous-day food
    Medication
    Morning behavior
    Morning mood
    School day vs weekend
```

The parent does not need to see this complexity.

The system should derive it.

---

# 14. Relative Interpretation and Baselines

Raw values are often insufficient.

Parents naturally evaluate today's experience relative to recent history.

For example:

```text
Recent days:
5 → 5 → 5 → 3
```

Today may feel "bad."

But:

```text
Recent days:
2 → 2 → 2 → 3
```

may feel "better."

Therefore analysis should distinguish:

* Absolute value
* Recent baseline
* Change from baseline
* Direction of trend
* Rate of change
* Variability

The system should support concepts such as:

```text
Today: 3/10
Recent average: 5.0
Change: -2.0
Trend: deteriorating
```

This should be available to both the Analysis and Prompting modules.

---

# 15. Temporal Comparison in Data Capture

Parents naturally think comparatively.

Instead of only asking:

> "How was your child's emotional state today?"

the system may ask:

> "Compared with yesterday and the previous few days, how was your child's emotional state today?"

Possible answers:

* Better
* About the same
* Worse

These comparative observations can be captured alongside absolute assessments.

Prompts should remain optional and should not create excessive burden.

---

# 16. Prompting Module — The "Science of Prompting"

Prompting should become a dedicated module.

The objective is **not maximum data collection**.

The objective is:

> **Maximum useful information with minimum caregiver burden.**

The Prompting engine should consider:

* Recent events
* Trends
* Anomalies
* New medications
* New foods
* New routines
* Interventions
* Unanswered questions
* Previous conversations/logs
* Time since something was last discussed
* Active Focus Areas
* What the parent tends to find useful

Example:

> "Ten days ago you mentioned starting a new medication. How has that been going?"

Or:

> "Your morning behavior has been lower than usual for the last four days. Would you like to record what was different?"

The system should understand context rather than simply generate generic reminders.

---

# 17. Adaptive Prompt Intensity

The system should eventually adapt the number and depth of prompts based on caregiver bandwidth.

Possible states:

### Low bandwidth

Ask only one or two high-value questions.

### Normal

Ask two or three useful questions.

### Reflective / engaged

Invite deeper reflection and exploration.

Parents should be able to control prompting:

* Done
* Not now
* Skip
* Stop asking
* Ask me more
* Remind me later

Prompting must never feel like an obligation.

---

# 18. Intelligent Follow-Up

The system should remember unresolved observations.

For example:

Day 1:

> "We started a new routine."

Ten days later:

> "How has the new routine been working?"

Or:

> "You previously mentioned that mornings were difficult. Is that still happening?"

This creates continuity.

Open Spectrum should behave less like a form and more like an intelligent assistant that understands the history of the child.

---

# 19. Analysis and Insights

Analysis should operate across the entire underlying dataset.

The system should look for:

* Trends
* Changes
* Correlations
* Differences between periods
* Differences between contexts
* Before/after changes
* Possible relationships
* Anomalies
* Missing information
* Contradictory evidence

Importantly:

> **Correlation should not automatically be presented as causation.**

The system should communicate uncertainty.

For example:

> "Morning difficulty was more common on days following less sleep."

rather than:

> "Lack of sleep causes morning difficulty."

---

# 20. Hypothesis Generation

Open Spectrum should eventually be capable of generating hypotheses from accumulated observations.

Example:

> "Mornings appear more difficult following nights with less than seven hours of sleep."

Or:

> "Behavior appears to have improved during the two weeks following the change in routine."

A hypothesis should be treated as:

**Something worth investigating, not a conclusion or diagnosis.**

A structured hypothesis might contain:

```text
Hypothesis
-----------
id
statement
created_by
created_at
focus_area
variables
supporting_observations
contradicting_observations
confidence
status
```

---

# 21. Parent-Defined Questions / Hypotheses

Parents should not have to wait for the AI to generate a hypothesis.

They can explicitly say:

> "I think X may be related to Y."

The system can then help structure the question.

For example:

Parent:

> "I think dairy might be affecting my child's mood."

Open Spectrum:

```text
Possible variables:
    Dairy consumption
    Mood rating
    Time between consumption and observation

Relevant history:
    Last 30 days

Suggested observation period:
    14 days

Potential confounders:
    Sleep
    School day/weekend
    Medication
```

This turns the application into an investigation platform.

---

# 22. Data Export — Parents Own Their Data

Parents should be able to download their data in standard machine-readable formats.

At minimum:

* CSV
* JSON

Export should support:

### All data

Everything recorded for the child.

### Date range

For example:

```text
August 1–August 31
```

### Focus Area

Everything relevant to a particular investigation.

### Multiple Focus Areas

A combined export around several investigations.

### Selected categories/events

Parent-selected subsets.

---

# 23. Focus-Area Export Should Include Relevant Data

A Focus Area export should not merely contain events explicitly tagged with the Focus Area.

If Open Spectrum used the following variables to investigate:

> "Difficult mornings"

the export might contain:

* Sleep duration
* Sleep quality
* Wake time
* Morning mood
* Morning behavior
* Food
* Medication
* Relevant routines
* Context
* School/weekend status
* Parent assessments
* Event timestamps

The export should make it clear which fields are:

### Raw observations

What the parent actually recorded.

### Derived measures

What Open Spectrum calculated.

### AI-generated interpretations

What the system inferred or suggested.

These must not be conflated.

---

# 24. Open Data Philosophy

Parents should be able to take their data elsewhere.

They could use:

* Excel
* Google Sheets
* Power BI
* Tableau
* Python
* Their own AI tools
* Other research/analysis systems

Open Spectrum should not become a closed ecosystem.

The long-term evolution could include an API in addition to CSV/JSON export.

---

# 25. Parent-to-Parent Connections

The product could eventually use profile information and Focus Areas to identify potentially useful connections between parents.

For example:

> "Another parent has a child around the same age and is exploring a similar Focus Area. Would you be interested in connecting?"

Potential matching factors might include:

* Age range
* Areas of interest
* Focus Areas
* Similar experiences
* Relevant profile characteristics

This should always be **explicitly opt-in**.

---

# 26. Privacy Principle for Parent Connections

Open Spectrum does not need to become the place where parents exchange their children's data.

The system could simply facilitate the introduction.

Conceptually:

```text
Profile similarity
        ↓
Potential match
        ↓
Ask Parent A
        ↓
Ask Parent B
        ↓
Mutual consent
        ↓
Introduction
        ↓
Parents decide what to share
```

The parents may then communicate outside Open Spectrum.

Important principle:

> **Similarity can create an opportunity for connection. It must never automatically create an opportunity for data sharing.**

---

# 27. Long-Term Vision: Hypothesis Marketplace / Community Science

A particularly interesting future direction is allowing parents to publish hypotheses.

Example:

> **Hypothesis:** Children who sleep less than seven hours tend to have more difficult mornings.

Other parents could:

* View the hypothesis
* Upvote it as something they want investigated
* Follow it
* Participate
* Contribute relevant observations

The system could show:

```text
347 parents interested
```

A hypothesis with sufficient participation could reach a **community quorum**.

---

# 28. From Hypothesis to Evidence

The long-term workflow could become:

```text
Parent observation
        ↓
Hypothesis
        ↓
Community interest
        ↓
Participants
        ↓
Define required variables
        ↓
Voluntary data contribution
        ↓
Aggregate observations
        ↓
Analysis
        ↓
Evidence
        ↓
Refined hypothesis
```

For example:

> "Does insufficient sleep correlate with difficult mornings?"

The system could determine that useful observations include:

* Sleep duration
* Sleep quality
* Morning behavior score
* Morning mood
* School vs weekend
* Potential confounding variables

It could then analyze voluntary contributions.

This begins to resemble **distributed observational research / community science**.

---

# 29. Design of Experiments

Eventually, Open Spectrum could help parents move from vague observations toward structured investigations.

Instead of:

> "I think X is causing Y."

the system might help formulate:

```text
Hypothesis:
X may be associated with Y.

Independent variable:
X

Dependent variable:
Y

Observation period:
14 days

Suggested observations:
A, B, C

Potential confounders:
D, E, F

Evidence:
...

Conclusion:
Insufficient evidence / supports hypothesis / contradicts hypothesis
```

This is a long-term capability, not necessarily an immediate implementation requirement.

---

# 30. Important Privacy Principle

Parents should be able to participate in community investigations without automatically exposing their raw data.

Potential levels of participation:

1. Follow a hypothesis
2. Express interest
3. Contribute an anonymized result
4. Contribute selected observations
5. Participate in a structured investigation

The parent should control the level of participation.

---

# 31. Shared Data Model Is the Foundation

All of the above depends on a strong, flexible underlying data model.

The system should conceptually separate:

### Child/Profile Data

Relatively slow-changing information.

### Event/Observation Data

Frequently changing observations.

### Context

Information that helps interpret observations.

### Assessment

How the parent evaluates the event.

### Tags

System and parent-defined vocabulary.

### Focus Areas

Questions the parent is currently exploring.

### Prompts

Questions generated or scheduled by the system.

### Analyses

Computations performed against observations.

### Insights

Interpretations derived from analyses.

### Hypotheses

Questions or explanations being investigated.

### Reports

Human-readable representations of evidence.

### Exports

Machine-readable representations of data.

---

# 32. Raw Data vs Derived Intelligence

This distinction is critical.

The architecture should preserve a clear chain:

```text
RAW OBSERVATION
       ↓
DERIVED MEASURE
       ↓
ANALYSIS
       ↓
INSIGHT
       ↓
HYPOTHESIS
```

For example:

```text
Raw:
Sleep = 6.5 hours

Derived:
Sleep is 1.2 hours below recent average

Analysis:
Morning difficulty occurs more frequently following
below-average sleep

Insight:
There appears to be an association between shorter
sleep and difficult mornings

Hypothesis:
Insufficient sleep may contribute to difficult mornings
```

Each layer should be distinguishable.

Do not overwrite raw observations with AI interpretations.

---

# 33. Recommended Architectural Direction

The implementation should move toward a modular architecture such as:

```text
                    Open Spectrum
                          |
             Shared Data / Domain Model
                          |
       +------------------+------------------+
       |                  |                  |
    Capture           Intelligence        Ecosystem
       |                  |                  |
   Logging           Prompting          Parent Network
   Voice             Analysis           Hypotheses
   Tags              Insights           Community
   Assessment        Focus Areas        Research
       |              Reports
       |              Export
       +------------------+------------------+
                          |
                     Data Layer
```

The exact technology implementation can vary, but the separation of responsibilities should remain.

# 35. What NOT to Do

The refactoring should avoid several traps.

### Do not build a rigid taxonomy

The child and parent's needs will evolve.

### Do not make every event a fixed schema

Different observations require different attributes.

### Do not treat record time as event time

Parents will frequently enter observations retrospectively.

### Do not make mobile a miniature version of desktop

Mobile and web have different jobs.

### Do not overwhelm parents with prompts

Prompting must optimize value vs burden.

### Do not treat AI hypotheses as facts

Clearly distinguish observations, associations, hypotheses, and conclusions.

### Do not lock parents into Open Spectrum

Data export is a core principle.

### Do not automatically share parent/child data

Peer connections and community research must be consent-driven.

---

# 36. The Product We Are Building

The immediate product may look like a logging application.

The architecture should assume that it will become much more.

At its core:

> **Open Spectrum is a system that helps parents observe, understand, and investigate their child's experiences over time.**

The parent provides observations and questions.

Open Spectrum provides:

* Structure
* Context
* Memory
* Analysis
* Prompts
* Insights
* Hypotheses
* Reports
* Connections

And eventually, parents can collectively investigate questions that no single parent could answer alone.

The long-term vision is therefore:

> **A parent-controlled, intelligent data and investigation ecosystem where individual observations can become meaningful insights, and meaningful insights can become collectively testable hypotheses.**

---

# 37. Key Architectural Principle for the Coding Team

When making implementation decisions, ask:

> **"Will this decision make it easier or harder for Open Spectrum to adapt to a new child, a new Focus Area, a new type of observation, or a new type of analysis?"**

Prefer designs that make those things easy.

The immediate goal is not to implement every future capability.

The immediate goal is to build the **flexible foundation that makes those capabilities possible without another major rewrite.**
